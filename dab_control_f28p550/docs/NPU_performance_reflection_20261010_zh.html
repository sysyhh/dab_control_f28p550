NPU 耗时复盘与后续方向

日期：2026-10-10。代码基线：b04537d（P5）；本轮仅研究、核对已有数据和补充说明，不重新加载开发板、不修改固件或模型。

1. 判断

当前较慢由小网络的使用开销、为了部署而扩大网络、以及生成代码效率共同造成，不能把 102.89 μs 认定为 F28P55x 的硬件下限。 也没有证据表明当前已经发生 NPU 未执行、时钟误分频、未完成常量复制等功能错误；四层硬件调用、完成中断、普通版输出与 RAM 镜像都已有实板检查。

与此同时，量化模型存在已确认的精度不足。它与运行速度是两个需要分别解决的问题：减少复制时间不会改善量化分辨率；采用低精度模型获得较短时间，也不能直接证明控制应用受益。

建议保留 FPU 作为当前控制基准，将下一阶段目标改为“验证 NPU 是否值得采用”，而非预设 NPU 最终必胜。 新工具链、较少补齐、较少层数以及混合计算有验证价值，但持续只调整复制循环，现有证据不足以支持最终低于 FPU 的承诺。

2. 当前时间主要在哪里

数据来自 P5 验收索引和 FPU 实板对照，均为 Vin=90 V、10 次预热、1000 次正式推理。当前普通版平均：FPU 前向 23.59093 μs、端到端 28.71550 μs；NPU 输出完成 96.05240 μs、端到端 102.89487 μs。

P5 详细计时内容 平均 μs 解释
四层参数装载 27.94138 CPU 向 NPU 写入权重、偏置等参数
四层指令装载 21.46308 每层重新写入指令，即使部分相同
四层寄存器配置 8.75276 设置运算和输入输出地址
输入量化 14.50189 16 项都做浮点缩放、取整和限幅，15 项恒为零
打包与层间复制 2.92607 CPU 整理各层数据
最后拆包 0.61333 还原输出存储格式
四层启动到完成中断 17.70328 包含硬件执行、等待及中断响应，不能视为裸运算时间
输出还原为 float 0.42000 已很短，优先优化它意义有限
详细计时版端到端 121.03644 比普通版多 18.14156 μs

参数和指令装载合计约 49.40 μs，占详细计时版端到端约 40.82%。由此可以确认数据与指令装载值得关注，但不能直接拿这些分段数值从普通版的 102.89 μs 中相减，更不能把余数称为硬件下限。

普通版最后完成到后台发现平均约 1.81 μs，最小端到端仍为 101.19 μs；单纯提高轮询频率缺乏足以消除约 74 μs 差距的依据。最小值同样包含软件和中断，不能替代独立的硬件测量。

源码依据：装载与配置、四层执行及输入转换、应用计时。NPU 时钟配置为 SYSCTL_NPUCLK_DIV_1；本轮未重新测量实际时钟，因而只能确认源码没有主动降频。

3. 哪些属于平台开销，哪些属于当前选择

问题 已有证据 判断
小网络要付出配置、传输与完成处理成本 本地四层装载与中断流程；TI 官方小型正弦模型也有 NPU 慢于 CPU 的案例 平台使用成本真实存在，但当前流程的每次写入不一定都不可消除
参数每层覆盖 NPU 的同一装载区 当前 TINIE_setup() 从相同基址写入每层不同参数 当前执行方式需要不同层参数；不能仅“初始化一次”就跳过其他层的装载
相同指令反复装载 前三层使用同一指令表，第四层使用另一表；每次推理全部装载 有减少重复的空间，但跨推理、复位、其他模型使用以及覆盖长度必须有失效规则
通道过度补齐 FPU 3→29→12→6→4，当前 NPU 16→32→16→16→4 属于先跑通时的保守选择，应重新按实际 PWCONV 约束核对，并非已证明的最小尺寸
输入输出仍采用 float 接口 输入仍对 16 项量化，输出仍还原 float 支持通用接口的代价；只保留实际变化项或整数接口值得独立验证
生成代码与版本 当前 NNC 2.1.0；官方 2.1.1 专门优化了 F28P55x setup 不能继续将旧生成代码的装载效率视为平台不可改变的性质
CPU 抢占与异步执行 当前计时包含控制/PWM 中断，NPU 每层完成后由 CPU 启动下一层 单次等待、CPU 占用及控制期限是不同指标，尚缺完整对照

FPU 网络矩阵乘加总数为 3×29 + 29×12 + 12×6 + 6×4 = 531；当前补齐网络为 16×32 + 32×16 + 16×16 + 16×4 = 1344，约为 2.53 倍。这是矩阵形状对应的计算量，不是精确 NPU 指令数；当前完整装载也没有根据零权重自动跳过的逻辑。

四层参数数组合计每次写入 506 个 32 位值，分别为 208、168、104、26；此外还有指令、配置与转换。面对只有 531 次浮点乘加的小网络，这些额外工作很容易抵消加速器的乘加优势；不能用芯片宣称的峰值算力直接除以 531 来预测应用耗时。

官方 PWCONV 规则及本地 config_pwconv.py 要求输入输出通道为 4 的倍数，不是所有层都必须至少 16。4→32→12→8→4 的矩阵乘加为 640，仅作为较少补齐的研究候选；它尚未编译、未量化核对、未实板测量，不能声明可直接替换或预报收益。TI NNC 2.1.0 Layer Patterns、TI NPU Guidelines

关于 FC 需要作准确区分：官方文档列出 FC 支持，不能表述成“F28P55x 不支持全连接”。本地 NNC 2.1.0 的 tinie.py 第 916～918 行在 C28 默认选择 TINIE_fullyConnected 软件实现，其内部测试开关可选择硬件分支；当前 Conv 改写解决了本地默认路径问题，但不是唯一可能的表达，也不证明它最优。该开关被源代码明确标为 TI internal testing，不建议当作已支持的生产选项直接启用。

4. 量化和模型设计的实质问题

当前路径是对既有权重做补齐、常量折叠、通道缩放和 PTQ；校准采用 90～140 V、步长 1 V 的 51 点，没有针对 NPU 重新训练。它是合理的迁移实验起点，但不是已经完成控制精度设计的模型。生成脚本

已保存的 501 点、步长 0.1 V 对照发现 92.2～92.5 V 存在无效候选输出，最大输出误差约为 [0.04887,0.03709,0.02695,0.04887]。数值报告

更直接的结构性证据是末层输出按 int8 × 0.015625 还原，四项值的间隔为 1/64；仅 T 的相邻量化格点，在基础周期 2500 时就相差约 39.06 个计数。若保持目前文档中“一个 PWM 计数”的目标，单纯增加校准点或做 QAT 无法改变固定输出量化格点本身；float 返回类型也不会补回已经丢失的信息。

因此后续数值方案应评估输出缩放/偏移、残差输出、部分层使用 CPU float 或重新设计模型，并对四项输出及最终 PWM 参数共同验收。QAT 可改善误差分配，但不保证解决当前末层分辨率问题；采用 2/4 位权重也不能因为理论传输较少就视为适合本控制任务。

5. 与同类项目是否同量级

最接近的公开资料是 TI 的 F28P55x 正弦回归 MLP，而不是大型分类网络：

TI 正弦模型隐藏宽度 CPU 单次 μs NPU 单次 μs 现象
16 22.3 25.2 小模型 NPU 稍慢
64 270.6 214.6 NPU 获得一定收益
128 1012 711.6 较大模型 NPU 收益增加

数据来自 TI SDAA185 §13.1～13.2，已核对 PDF 第 32 页表格。官方 64 宽例子是 1→64→64→1；它与本项目层数、精度和部署条件不同，且表中未完整列出时钟、存储位置、中断和计时边界，CPU 列也不能认定等同本项目手写 FPU。

因此当前约 103 μs 属于同平台公开案例覆盖的数十至数百微秒范围，没有慢到足以凭时间认定硬件使用错误；但官方小模型 25.2 μs 也说明 103 μs 不是该平台的统一最低耗时。它不能证明本项目性能已经合理，更不能用另一个模型的 25.2 μs 保证本项目一定能达到。

TI 官方 grid_stability 的 F28P55x NPU 相对 CPU 有约 4 倍收益，但 CNN 分类模型与这里的小 MLP 不同；induction_motor_speed_prediction 的 9.45 μs 则属于 F29H85x，不能引用成 F28P55x NPU 成绩。更多条件与直接来源见 外部证据核对。

6. 能否超过当前 FPU

有研究希望，但目前无法承诺；保持当前四层补齐模型，仅继续小幅调整装载代码，证据并不乐观。 从普通版 102.89487 μs 降到 FPU 28.71550 μs，需要再减少约 72.09% 的端到端时间；P5 只有 4.26% 的收益不能外推成后续轮次也会持续有足够收益。

较有价值的机会包括较少补齐、减少硬件层数、减少参数/指令装载、整数输入以及 NNC 的 setup 改进。特别是 NNC 2.1.1 release notes明确提到 F28P55x NPU setup 优化；当前尚未实测，且可能与 P4/P5 已做优化重叠，不能先把收益相加。

NNC 2.1.2 release notes又要求应用链接使用 C2000Ware 26.0 或更新。当前基于 DigitalPower SDK 5.05.01.00 所带较旧 C2000Ware，升级应放在独立环境中核对生成代码、接口、链接及实板结果，而非直接替换已验证库。

当前还没有测出 CPU 实际占用和每次 NPU 中断最长持续时间。NPU 异步执行可以让 CPU 做其他工作，但参数装载、输入转换和层间推进仍由 CPU 完成；即使最终耗时没有胜过 FPU，也需量化 CPU 占用收益后才能判断是否值得采用。

FPU 也还可以评估固定输入折叠、编译优化或更适合单变量函数的实现；所以超过“今天的手写 FPU”与超过“同等精度下较优的 CPU 实现”应明确区分。

7. 建议的有限验证与停止条件

优先级 要回答的问题 可执行的验证与判定
1 工具链是否贡献了大量可避免开销 独立环境对照当前 P5 与新版 NNC，保存卸载摘要、每层装载数量、源码差异和库摘要；同条件连续 1000 次测试，比较普通版端到端与最大值
2 103 μs 中有多少由控制任务和完成处理造成 保留现有保护，在不输出功率的专用测试中分离外设负载与推理；同时测 CPU 占用、NPU 中断长度和控制期限，隔离结果只用于诊断，正式验收恢复原条件
3 当前 16 通道补齐是否必要 用较少补齐候选进行浮点等价、量化参考和编译硬件卸载核对；只有全部通过后才实板扫输入并测时
4 当前输出量化是否满足应用 明确允许的相位、周期和最终 PWM 误差；比较 FPU、量化软件参考和板上输出，覆盖量化跳变点，不放宽保护来取得计时成绩
5 是否值得重构网络或采用混合计算 将通过精度验收的较浅模型或 NPU/CPU 混合路径与同精度 CPU 比较；同时看延迟、CPU 占用、最坏中断及维护成本

整数输入的 TI 官方 skip_normalize 选项是可评估手段，但应用仍要负责正确的缩放、取整、限幅和输入存储格式；不能只是删掉原来的量化步骤。参数/指令复用也必须先有复位和模型切换后的失效规则。

停止条件应是工程目标而不是轮数：如果已验证版本在满足同等精度、控制期限后既不比 FPU 快，也没有明显 CPU 占用收益，就停止为本小网络继续深改运行库，保留 FPU。若只有改变精度才能更快，应明确这是精度与速度交换，不列为同等质量下的 NPU 加速。

8. 本轮核对方法

执行 python dab_control_f28p550/tools/analyze_npu_reflection.py 重算矩阵规模、每层参数写入数量、分段占比、目标差距和输出量化间隔，并检查所用归档及当前库摘要。机器可读核对结果

执行 python tools/c2000_debug/verify_benchmarks.py <summary.json> ... 可复核所引用的 FPU 和 P5 原始快照；本轮未新增实板计时。外部来源、未确认条件及版本差异另存于 外部证据核对。
