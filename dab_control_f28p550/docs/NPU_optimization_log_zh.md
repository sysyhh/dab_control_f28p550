# NPU 耗时优化记录

所有轮次保留功率输出禁止、1 ms 超时和现有输出检查。软件验证通过表示构建及程序逻辑通过，实际耗时和硬件输出仍须开发板复测。

已提交历史：基线 `8344686`、P0 `aeb8cd4`、P1 `1bd4abe`、P2 `ef9a527`。后续提交通过项目根目录下 `git log --oneline` 查看；不必切换历史版本即可用下述选项逐级复测。

## 基线

优化前 Git 提交：`8344686`。用户提供的 1000 个板上样本：FPU 端到端平均 28.69056 μs，NPU 端到端平均 268.50498 μs，NPU 完成平均 253.16565 μs、提交平均 74.51850 μs；对应测试输入未随该组统计提供，复测时需补记 Vin。

## P0：可关闭的分段计时

生成模型库时添加 `--detail-profile`，再重新 Build NPU 配置。`g_nnNpuDetail.instrumented=true` 表示库带详细计时，`stage[]` 每项格式与 `g_nnTiming` 相同；同类步骤在一次任务内累加后记一个样本，预热与冻结规则相同，`lastCalls[]` 显示最后一项任务的调用次数，`invalidPairs` 应为 0。

| stage 下标 | 内容 |
|---:|---|
| 0 | 输入量化 |
| 1 | 数据打包或优化后的紧凑数据复制 |
| 2 | 数据拆包 |
| 3 | 隐藏层间处理 |
| 4 | 四层参数装载时间总和 |
| 5 | 四层指令装载时间总和 |
| 6 | 四层寄存器配置时间总和 |
| 7～10 | 各层启动至进入完成中断，包含中断响应延迟 |
| 11 | 最终 FLOAT32 输出还原 |

详细计时的计数读取和函数调用会增加耗时。最终性能比较必须重新生成不带 `--detail-profile` 的库并重新 Build；该版本在编译时移除详细计时调用，`instrumented=false`、分段样本为零，原有提交/完成/端到端统计继续有效。

本轮检查：带计时及普通库均用真实 TI 工具构建，接口测试覆盖预热排除、分段累加、输出拒绝、超时与功率启动禁止。尚无本轮板上实测收益。

## P1：消除隐藏层间重复浮点运算

三处隐藏层输出是无符号 8 位数；当前模型使用 64、128、256 三个二次幂比例、零偏移和 0.5 取整偏置。原处理对 0～255 的每个值均返回原值，因此替换为逐元素复制；保留 NPU 内部激活操作、首层输入量化和末层输出还原。

生成脚本默认 `--optimization-level 1`，指定 `0` 可重建原计算路径。脚本检查原表达式、通道数和生成常量，遇到不同模型立即停止；同时保存 `lib1.reference.c` 供比较，避免重新生成覆盖优化。

`tools/verify_npu_runtime.py` 提取新旧生成代码中的真实 C 函数，采用严格浮点编译，对三个函数的所有 64 个通道位置各遍历 256 种值并检查输出边界。此检查保证已替换的 CPU 步骤等价；完整 NPU 输出仍须在板上核对。

## P2：直接复制层间紧凑数据

三个隐藏层连接处分别复制 16、8、8 个 C28 存储单元，替代原来的拆包、恒等变换、重新打包。C28 一个存储单元是 16 位，TI 的 `__byte` 每次处理其中一个 8 位通道；原目标缓冲区和下一层输入/输出地址保持不变。

脚本默认 `--optimization-level 2`，生成时检查 TI 打包实现、三个连接处的调用顺序和源/目标范围不部分重叠；相同地址允许原位保留数据。验证程序编译原生成的拆包/打包函数并模拟 C28 存储语义，对 65536 种存储单元值逐一比较 8 单元和 16 单元复制，同时检查边界；首层打包和末层拆包仍保留。

## P3：NPU 配置及数据处理代码在 RAM 中运行

默认生成级别提升为 `--optimization-level 3`。使用独立 `.dab_npu_ramfunc`，Flash 保存代码镜像，`DAB_NN_init()` 在 NPU 初始化前复制到 LS2；NPU 配置、启动、中断、首末层数据处理及层间复制在此区域运行，数据、权重、输入输出与 GS1 工作区位置不变。

普通版本链接结果：运行地址 `0x9000`，使用 `0x337` 个 16 位存储单元，即 823/2048 单元，代码镜像 1646 字节。反汇编已检查初始化路径使用正确的 Flash 源地址、LS2 目标地址和复制长度；实际脱离调试器的上电启动以及运行收益仍需开发板验证。

原有 LS0/LS1 的控制、保护和 FPU RAM 代码继续单独分配，详细计时版本也要检查 LS2 未超出容量。构建检查读取新生成的 map 文件，核对主要函数运行地址和 GS1 工作区位置，并确认已删除的隐藏层转换未被链接。

## P4：参数与指令装载循环展开

当前生成脚本默认使用 `--optimization-level 4`。将参数和指令的逐项装载改为每次处理四项，再单独处理不足四项的尾部；仍加载全部数据，不缓存、不跳过任何层，保持原 TI 运行库的写入次序、32 位数据宽度及隔一个 32 位位置写入的地址间隔。

生成脚本检查原有两段循环必须完整匹配，避免将补丁套到不相容的 TI 运行库。装载辅助函数强制内联，继续在 LS2 中运行；修改仅减少循环控制开销，不改变模型、量化常量、NPU 计算及中断处理方式。

软件验证提取实际生成的装载函数，对长度 0～516 的每一种情况逐一比较原循环结果，覆盖所有尾部情况，并核对未使用间隔与两端边界保持原值。TI 编译和链接检查继续确认 LS2 容量、函数地址与 GS1 工作区。

### P4 自动实板结果

Vin=90 V、预热 10 次、正式 1000 次，普通和详细计时版本各完成三轮独立加载测试。P4 普通版本三轮的端到端平均值均为 107.47151 μs，较 P3 普通版本的 149.07457 μs 降低约 27.91%；恢复普通库后另外重新加载复测，作为最终交付检查。

| 普通版本统计项 | P3 μs | P4 μs | 耗时降低 |
|---|---:|---:|---:|
| 提交调用 | 59.53495 | 43.56228 | 26.83% |
| 输出完成 | 141.76094 | 99.91755 | 29.52% |
| 端到端 | 149.07457 | 107.47151 | 27.91% |

| 详细计时分段 | P3 μs | P4 μs |
|---|---:|---:|
| 四层参数装载合计 | 55.69861 | 29.98538 |
| 四层指令装载合计 | 42.27066 | 22.58032 |
| 四层寄存器配置合计 | 9.38047 | 10.28604 |
| 输入量化 | 14.80689 | 15.12477 |
| 四层启动至完成中断合计 | 22.43979 | 17.89835 |
| 端到端 | 175.01425 | 124.47202 |

装载两项的详细计时合计由 97.96927 μs 降至 52.56570 μs，确认本轮优化命中了主要耗时。其他分段仍包含中断响应与抢占，随运行时序变化而变化，不能将等待时间变化解释为 NPU 运算本身变快；详细计时版本仍不用于正式速度比较。

所有成功轮次均为 1000 个正式样本、10 次预热、无拒绝或超时、待机且四路功率 PWM 关断。两种 P4 版本输出均与 P3 的 `[0.4375,0.25,0,1]` 一致，详细计时调用次数不变、`invalidPairs=0`；本轮的板上数值检查限于 Vin=90 V，全范围精度验收仍未完成。

相对同条件 FPU 的 28.71550 μs，P4 端到端仍约为 3.74 倍。下一步可评估装载源常量移到 RAM、减少固定输入的重复量化，以及带严格失效条件的指令复用；本轮尚未实施这些改动，也未开放功率闭环。

本轮共七轮成功实板测试，原始数据与检查索引见 [P4 实板验收报告](../../tools/c2000_debug/p4_benchmark_verification.json)。恢复模型时曾因复制保留旧时间戳而未重新链接，详细计时开关检查将该轮拒绝，未计入成绩；统计工具现已强制重新编译 NN 并重新链接，再次实板验证成功。

`python tools/c2000_debug/test_rebuild_nn.py` 可离线复现旧时间戳跳过构建的情形，并验证强制编译失败时不会加载旧程序。最终交付为 P4 普通库，`detail_profile=false`，板上也已加载该版本并暂停。

## 开发板复测方法

1. 使用 `CPU1_LAUNCHXL_NPU_FLASH`，保持 `DAB_AUTO_START=0`、`DAB_BOARD_CONFIG_CONFIRMED=0`，连接 USB 即可做 NN 基准测试。基准测试用指定的 Vin，仍须确认程序处于停止状态；功率输出批准标记继续为 0。
2. 每次重新生成库后都在 CCS 完整 Build、重新加载，并从初始化运行；P3 必须经过初始化复制，不能直接跳转到主循环。
3. 设置 `g_nnBenchmarkVin=90.0f`、`g_nnBenchmarkIterations=1000`、`g_nnBenchmarkWarmup=10`，最后设置 `g_nnBenchmarkRequested=true`。运行至 `g_nnBenchmarkState=2` 且统计冻结后读取，期间不打断点。
4. 每一级记录生成清单中的 `optimization_level`、`detail_profile`、库 SHA-256、测试 Vin、`g_nnTiming`、`g_nnLastOutput`、`g_nnTimeoutCount` 及故障状态。应完成 1000 个正式样本、拒绝输出及超时均为 0；同一输入的四项输出应与级别 0 一致。
5. 对照同一输入、相同中断与外设条件下各级的 `npuSubmit`、`npuCompletion`、`endToEnd` 的平均/最小/最大值，再与相同条件的 FPU 比较。各步骤包含中断响应或抢占，不能将完成时间当作裸 NPU 周期。

在 `ccs_projects` 目录执行以下命令，N 替换为 0、1、2、3 或 4；当前默认级别为 4：

```powershell
review_20261003/npu_integration_20261009/python310/python.exe dab_control_f28p550/tools/compile_dab_npu.py --optimization-level N
```

定位剩余耗时时，在相同命令末尾加 `--detail-profile`，Build 并复测，保存 `g_nnNpuDetail`。`invalidPairs` 应为 0；四层启动/完成各一次，参数/指令/寄存器各四次，级别 2/3 的隐藏层转换不再有样本，紧凑数据复制计入 stage[1]；分段统计涉及计时调用，须与不带详细计时的正式成绩区分。

正式速度对比使用不带 `--detail-profile` 的库；当前交付版本默认如此。复现软件检查：

```powershell
python dab_control_f28p550/tools/verify_npu_runtime.py
python review_20261003/npu_integration_20261009/verify_integration.py
```

### P3 后的实板统计反馈

用户本次提供 1000 个样本，150 MHz，统计已冻结、拒绝输出为 0；未同时提供测试 Vin、完整输出、超时计数及已加载库的身份，因此与旧数据的比较仍需核对测试条件。

| 指标 | 优化前平均 μs | 本次平均 μs | 降低 |
|---|---:|---:|---:|
| 提交调用经过时间 | 74.51849 | 59.97135 | 19.52% |
| 启动至最终输出完成 | 253.16562 | 141.68356 | 44.04% |
| 启动至后台发现完成 | 254.99263 | 143.43584 | 43.75% |
| 端到端 | 268.50494 | 149.05829 | 44.49% |

按现有两组数据，端到端改善约 1.80 倍，但仍为此前 FPU 的 28.69056 μs 的 5.20 倍。最终完成到后台发现平均仅差 1.75229 μs，改善后台轮询无法解释剩余约 120 μs 的差距；而提交调用本身已接近 60 μs，需要继续检查首层数据处理、参数/指令装载和配置。

`npuSubmit` 和 `npuCompletion` 共用启动时间点，前者包含在后者之内，不能相加；两项均可能包含中断占用。下一次应在级别 3 下启用 `--detail-profile` 获取 `g_nnNpuDetail`，同时补记 Vin、输出、超时计数和库清单，以区分装载、配置、层间处理与各层启动到完成中断的耗时；详细计时版本仅用于定位，正式提速结论仍用关闭详细计时的版本。

当前已交付不改变模型数学含义的 P0～P4，并完成自动实板统计。后续继续评估常量读取、固定输入量化和指令复用；指令缓存需要核对各层指令的差异、覆盖方式与复位失效条件，不能仅因为代码尺寸相同就复用。

目前量化模型在 92.2～92.5 V 仍存在已记录的无效输出；上述优化不会消除量化误差，因而仍不允许用于功率闭环。提高精度、开放功率控制以及判断优化后是否快于 FPU，均需另外的数值与实板验收。
